## A. Compact and usable one-thumb steering (P0, test first)

### Existing control semantics to preserve

Player drives via horizontal, phone landscape steering strip using absolute touch x → virtual steering [-1,+1] with a neutral zone and four stable effective steering levels per direction (±0.25/0.5/0.75/1), rapidly eased; lift/cancel/blur resets input swiftly to neutral. Separate gas/brake multi-touch pointer(s); handedness swap moves steering to opposite thumb. Desktop A/D uses same virtual steering authority.

### New ergonomic targets

- Inspect actual CSS/DOM/canvas and pointer normalization. **Shrink the steering ACTIVE full-lock-to-full-lock span**, not just the decoration; candidate **120–160 CSS pixels total active travel** in the Pixel 8 landscape phone viewport, with final width tuned by a real browser inspection and owner hardware follow-up. Responsive bound can adjust for smaller screens. This should be achievable without lifting the thumb or crossing large fractions of the screen.
- Position the active strip near the natural resting thumb region on either handedness, NOT spanning most of the bottom edge. Separate large-enough vertical touch capture zone from smaller horizontal travel: big reliable touch target, short movement distance. Avoid losing touch when finger drifts slightly above/below bar. Need accessible visible end stops and neutral center; 0 and ±1 must be reachable without edge clipping. Consider short, intentional inward-outward swipes and direct tap to desired absolute position with no microscopic precision.
- Retain center deadzone + hysteresis appropriate to the new shorter travel, so ~1–2 CSS-px fingertip jitter does not fling the car between levels; map bands by normalized travel, do not blindly reuse old pixel thresholds. Retain short 100-ms step easing and ~60-ms neutral release as baseline unless the source differs; no long slow steering response or physical yaw inertia.
- DO NOT shift the pedal cluster, needle gauge or camera into unreadable positions. Check both handedness choices and portrait-to-landscape/fullscreen/PWA resizes, safe area, touch ID coexistence and scoped long-press suppression.
- Give ability for user to reach full ±1 and quickly reverse sign. Avoid a secondary "child mode", hidden auto-steer, giant settings screen or disabling steering range. One comfortable default should work for both child and adult.
- Tests should measure actual **CSS px center-to-full-lock distance** before vs after on e.g. 844×390 and 960×432 landscape, not just normalized values. Also check touch across all nine quantized states, touch slides/tap, rapid reversal, blur/release; test gas held simultaneously. Physical Pixel 8 thumb comfort is USER UNVERIFIED until physically tested.

## B. Six-speed arcade automatic drivetrain (P0)

- Implement genuine gear state `1..6`, RPM state with idle/min/redline and speed-to-RPM per gear (simplified arcade ratios are fine), throttle and torque curve. Five discrete upshifts during a normal full-gas 0→300 run, distinct RPM rises/drops and brief controllable torque interruption; downshift under braking/coasting with hysteresis/no hunting. No new manual input.
- Gear changes should be **noticeable and pleasant**, not a dashboard-only animation. Gear state and RPM influence acceleration and audio. Avoid sound or power glitches when pausing, switching/restarting L2 or getting off-road.
- Display small current-gear indicator next to existing analog speedometer, without obscuring mobile HUD. Do not overhaul the entire cockpit or add transmission tuning menus.
- Target 300 km/h legitimately attainable on a sufficiently long level road via normal throttle, with the existing **1.75× world pace** mapping intact and actual distance/road geometry consistent. Analog and numeric speed display readable through 300.
- IMPORTANT: preserve Arcade Lateral Balance steering, independent visual drift pose, off-road slowdown/bounded shoulder. Existing calibrated bend difficulty near 230 indicated km/h stays what it was; **300 km/h may require more careful speed/brake choices**, but never secretly change corner grip/curve pressure to make every old sweep a no-brake 300 bend.

### Acceleration feel — calibration, not dictated real-car statistics

Reference images supplied by owner: in the classic 2003-era racing sequence, HUD is ~0 mph at start and ~185 mph (~298 km/h) by ~19s, with visible 1→6 gear progression; this is **a visual observation of that reference, not a physics spec**. Owner finds OUR current top speed arrives too quickly.

1. Benchmark THIS game's current full-throttle time `0→100`, `0→200`, `0→238` before changing it, and record actual indicated speed vs time.
2. First candidate **0→100 around 4–6s**, **0→200 around 10–16s**, **0→300 around 20–28s**. These are FIRST TEST targets; choose based on present v0.7C baseline, rpm/shift pleasure and responsiveness, not a hard racing-sim metric. Report actual values and five upshift speed/time/RPMs. If 20–28s feels too short/long after browser driving, adjust and document.
3. Do not let game instant-speed boosts, test overrides or altering 1.75× scale masquerade as real acceleration. A test/dev long straight is okay to make 300 reachable; ordinary game remains human-driven.
4. In v0.7C short L2, give dev/test a rolling-start option only if needed to sample 6th gear; normal user start semantics unchanged, and no hidden autopilot.

## C. Engine audio: fuller, gentle to ears, six-shift rhythm (P0)
