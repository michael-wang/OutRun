## P0-B — Every screenshot saved automatically to a dedicated WINDOWS directory

### Local dev/test default

**When running the project Vite development server on Windows**, automatically persist every successful capture (including captures made from PC with DS4 and Pixel 8 via LAN) to a dated, gitignored destination:

`C:\astra-dev\OutRun\captures\YYYY-MM-DD\`

Use a small **Vite DEV-ONLY** middleware endpoint (`configureServer`, not in production build) to accept captured PNG bytes and minimal matching frame metadata, generate a unique server-side basename, and write PNG atomically. Example basename `20261028-184200-S01-v083-seed1-s08426-0007.png`. Server adds a monotonic/random collision-proof suffix; no overwrite. Optionally save matching `.json` sidecar with **time, actual stage code, seed, s, biome, speed, grade, steer, roadX, vehicle pose, per-wheel contact diagnostics when available, screenshot frame timestamp**. Camera must capture the actual rendered scene, not simply metadata. The path must not be supplied by untrusted URL/request data.

- **Security:** Vite configureServer only, fixed capture directory rooted at project; no arbitrary filesystem path, no public production endpoint, no CORS enabling other origins, check Origin/host where applicable; cap PNG byte size (e.g. 8MB) and bound request rate/queue so a malicious LAN page can't fill a drive. Validate PNG signature and respond explicitly. Do not save traffic from untrusted external origins or store extraneous gamepad input histories. `captures/` gitignored; do not commit user screenshots.
- **Completeness:** each button press triggers one screenshot; 10 distinct presses produce **10 distinct, valid PNG files**, even when within the same second. Consecutive photos never replace a previous file. Show small non-blocking "Saved /captures/YYYY-MM-DD/name.png" feedback plus running count, and make output path easy to copy/discover from UI. On failure, show actual error and preserve captured bytes via available browser fallback rather than silently losing user's evidence.
- **Pixel LAN:** same-origin `http://192.168.1.105:5173` page POSTs to the running Windows Vite development server; PNGs are saved on the **Windows PC** under its captures directory, not into the phone's filesystem. Fullscreen/Photo UI still works across portrait/landscape/PWA constraints. Test both desktop localhost and network-host usage; do not hardcode 192.168.1.105.
- **Without local dev middleware** (production/PWA/offline or server not reachable): don't pretend arbitrary-directory writing is permitted. Provide a simple safe browser fallback: unique PNG download when allowed and/or durable local queue with clear "not yet saved to PC" UI plus user-initiated export. It must be obvious when a photo was NOT saved to the designated Windows directory. No heavy photo cloud service, accounts or gallery framework now.

Browser security reality: `showDirectoryPicker()` requires a supported browser, a secure context and user interaction. Do not make it an implicit requirement for Pixel 8 LAN HTTP or claim that browser JS can silently access arbitrary user folders. Dev-only Vite middleware is the chosen immediate path.

**Actual photo 1:** steep curved canyon road; tire penetration/airborne impression; snapshot diagnostic grade approx `+0.369`, steer `-1`, center `surfaceGap≈0.010m`. This near-zero center sample does NOT validate wheel contacts. Do not treat the photo alone as certainty about source root cause.

Inspect source for road-mesh world surface evaluation vs current scalar height helper; car world transform, pitch/roll/yaw visual, four tire rotations/positions, wheel radius, chassis center/bottom and shadow. Identify which transform space causes visual mismatch. Do not replace proven Arcade Lateral Balance with full rigidbody engine.
2. For each tire calculate world-space actual contact patch (front-left, front-right, rear-left, rear-right) based on **visual body pose incl yaw, steer, roll and wheelbase/trackwidth**, sample **the same rendered road surface** beneath that footprint (including grades, transitions, curved road and variable width). Prefer one shared road surface evaluator or geometric barycentric sample consistent with actual mesh; avoid merely using road center grade at car pivot. Measure each tire-bottom ↔ rendered road top delta in meters; include road sample/world positions in debug metadata. For travel offroad, sample corresponding shoulder safely.
3. Apply a **lightweight arcade visual suspension/pose correction**: road-aligned chassis pitch/roll and small per-wheel compliant offsets if necessary, blend/smooth without frame-rate-dependent behavior. Avoid wheel penetration into solid road, visibly floating contact, wheels detached from fenders and body jumping/rolling unpredictably. Preserve fun exaggerated yaw/drift visual but decouple it from wheel vertical attachment; only VISIBLE transforms, not physical drive authority or road-relative x.
4. Improve contact cues via subtle road-conforming wheel shadow/contact decals as needed, not a giant dark rectangle or shadow pretending to hide blatant clipping. Do not turn actual ground clearance into "negative height" to mask a problem.
5. Test static steep ascent/descent, crest/trough, curve+grade together, flat straight, drift at 150/300, road width changes and shoulder. Sample per-wheel residuals, collision/road support continuity and visually inspect screenshots. A steady contact error target of a few centimeters is useful, but USER visual acceptance is decisive. If road geometry actually generates a hole or misaligned triangle, fix actual surface too.

## P0-D — Scenery continuity through cheap L3 geometry and occlusion

**Actual photo 2:** at approximately `s=8,426m`, ~235km/h, coast/city visual. Left far road appears suspended with empty space under segments; right city row has little behind it. Current low-poly style can be beautiful; don't pursue photorealism. **Use a small set of procedural reusable low-poly shapes** that hide emptiness and create a coherent world at normal chase-camera viewpoint.

- **Road needs support:** each generated road section's edge/shoulder must visibly meet terrain, coast cliff/embankment, retaining wall or intentionally supported bridge. Generate support/terrain skirts following road elevation and road curve, NOT flat global fill clipping road. If a high ocean crossing is deliberate, create simple bridge deck + occasional supports, not a free-floating road ribbon. Avoid double-sided z fighting and mountain meshes obstructing road (older v0.4 regression).
- **Coastal foreground/midground:** low-poly coastal rock slopes between road shoulder and waterline, compact repeating cliff segments/strips; horizon water and sky remain visible. Road support should adapt to climb/descend across terrain.
- **City:** first facades are not enough. Make a minimal second tier of simple box/silhouette masses or 2.5D backplates with varying height/roof/color plus a shared ground block. The cheap row behind creates apparent depth without modelling every window or rear wall. Small variation deterministic per Stage seed so repeated units aren't identical.
- **Canyon:** existing lowpoly mesa/cliff assets used as large irregular silhouettes at medium/long distance with visual layering/occlusion, plus generated terraced ground supporting high curves. Keep canyon cliffs from blocking road view.
- **Long distance:** controlled distance fade/fog, horizon silhouettes and coarse low-poly terrain, to avoid seeing the *end* or *underside* of geometry. Fog is visual polish, NOT a substitute for mid-range proper road supports. No infinite scene or full urban world.
- **Three visual bands** (near: truthful road/shadow; mid: continuous terrain/city blocks; far: cheap silhouettes/sky/fog), reuse InstancedMesh/batched geometries/materials if feasible, deterministic generation from L3 biome tags and road profile. If current project has scenery placement engine, extend it, not a parallel massive generator. Limit object/draw-call and Pixel 8 GPU budgets; don't add thousands of individual objects or huge textures.
- **Generalize to random Seeds:** not just handpatch `S01-v0.8.3-r1-1-ALB1`. Cover city/coast/canyon transitions, high grade, 2–8 lane width, road bend and different horizon angles. Preview from chase camera before marking PASS; no art director bluff or fake screenshots.
