# v0.3.2 — Arcade Pace Experiment

**Product owner decision:** v0.3.1 still feels much slower than OutRun 2. Perceived speed is a **go/no-go gate**, above all new artwork, drift, track and scenery features.

**User hypothesis:** multiply the *scene's movement* at indicated 234 km/h by approximately 2×.
**Engineering decision:** test this in a coherent vehicle/world motion system with tunable arcade pacing — **do not double scenery motion independently**.

## Observational evidence (not a controlled scientific comparison)

- User's new first video (~43s): First Drive v0.3.1 reaches and mostly stays at indicated **234 km/h**; surrounding coast road visually feels subdued.
- Second video (~42s): OutRun 2 speeds rise into **~175–180 mph** (about 282–290 km/h); near road, shadows, buildings and palms flow much more aggressively across the screen.
- A rough 720px-width, 10fps optical-flow check on nonidentical high-speed stretches found 75th-percentile near-road feature travel around **14px per 0.1s in First Drive vs 34px in OutRun 2**, and median about **8.5 vs 12.6px**. Conditions differ (road geometry, texture, camera steering, actual mph), so these numbers **do not** prove any precise speed factor. They do support the user's perception.
- Codex had measured ~**64.92 m/s** at indicated 234 km/h in v0.3.1. That supports roughly correct real-speed arithmetic, **not** automatically satisfying arcade visual speed. Three.js has no fixed road-travel speed limit.

## The implementation hypothesis and nonnegotiable distinction

### Chosen main treatment: speed-dependent **arcade world pace**

Expose a test-only target parameter `highSpeedPace` with four allowed values **1.0, 1.5, 1.75, 2.0**, starting with **1.75 default** (not a promise of the final tuning).

Use one coherent travel integrator for the car's world displacement and all gameplay-relative progress. Example of an implementation concept — adapt to existing source architecture, don't blindly paste pseudocode:

`effectivePace = 1 + (highSpeedPace - 1) * smoothstep(50, 200, indicatedSpeedKmH)`

`effectiveTravel = physicalGameSpeed * effectivePace * deltaSeconds`

- At low speeds, pace remains around 1×; it approaches the selected high-speed target when the indicated speed exceeds ~200.
- **Apply to real vehicle motion and derived camera/track-relative projections**, not merely UV-scrolling background/props while leaving the car at the old speed. All world-space objects, collision tests, render transforms, road/spline progress and sound cues must describe **the same motion**.
- If existing code computes longitudinal + lateral velocity or heading-based world pose, keep it coherent: do not multiply only one component while breaking drift trajectories or collision/projection. If yaw response becomes too slow relative to faster movement, tune active player-controlled steering response **without automatic curve following**.
- Treat indicated km/h as an intentionally **arcade-style speedometer** once the motion is boosted; maintain a dev-only honest effective-world-velocity readout. Don't falsify performance/physics claims or only alter the HUD number.
- Off-road penalty affects true gameplay travel, not just shown speed; no auto-centering, shoulder excursion remains bounded; inward steering lets players recover.
- Simulation remains time-step independent at 30/60 FPS, with interpolation or fixed-step logic as appropriate. Check segment streaming/culling when motion crosses more distance per frame.

### A/B test surface

Support a **development-only**, deterministic A/B variant selector (`?pace=1.0`, `?pace=1.5`, `?pace=1.75`, `?pace=2.0` or equivalent). For the shipped prototype the default is `1.75` pending human playtesting.

- Same start pose/track seed, camera FOV/dolly/framing, display speed, scenery, and quality across variants.
- Make changing variants on Pixel 8 practical: an optional small developer overlay or direct query URLs; no redesign of permanent game Settings.
- Include a stable straight and a moderate bend. The high pace must not make the game impossible to steer: if necessary tune **player steer/yaw authority** in a documented way, then verify no unintended lane assist.
- Run clips at ~80/150/234 indicated km/h and record actual game distance/sec, curb-post and lane-dash cadence, and frame timing. The high-speed target at **234 km/h** will be near **113.6 m/s** for 1.75× and **129.8 m/s** for 2.0× if the baseline ~64.92 m/s is retained. Record actual measured values; don't assume these are achieved.
- Compare a continuous launch-to-high-speed run and stabilized low/high clips; inspect actual browser motion, not only screenshots or a unit-test PASS.

### Secondary treatment — only if velocity boost still underwhelms

A 2017 published study found a **wider geometric FOV** can increase speed perception in 3D racing games, whereas strong motion blur can decrease it. If the primary A/B variants remain flat, experiment separately with **one wider fixed FOV** and re-tune fixed chase distance to preserve the existing ~24% onscreen car width and forward visibility. Do **not** return to speed-driven FOV/dolly zoom, excessive screen shake, blur or particle spam.

Study: https://eudl.eu/doi/10.1007/978-3-319-55834-9_14

## Product constraints / non-goals

- Preserve v0.3.1 art and large-car framing; don't solve velocity by shrinking the car or making visual content unreadable.
- No new biomes, difficulty overhaul, dramatic drift/tires, convertible or character animations this version. Those requests remain in `docs/ARCADE_DESIGN_BACKLOG.md`.
- No more loops of "add decorative roadside objects, declare success" without the new A/B human decision. Roadside markers are already enhanced in v0.3.1.
- Pixel 8 actual play remains a human gate. Emulation can verify layout/logic but not real device frame rate or subjective thrill.

## Required decision deliverable

Provide a locally playable A/B speed selection on the Pixel 8, actual clips at each variant, quantitative distance/marker evidence, and a concise answer to:
**At what multiplier, if any, does the game finally feel like a fast arcade racer without becoming uncontrollable?**

Codex cannot self-certify subjective speed GO; the owner decides after playing. If even 2.0× feels weak, flag NO-GO and diagnose fixed projection/scales rather than arbitrarily increasing to 3–4×.
