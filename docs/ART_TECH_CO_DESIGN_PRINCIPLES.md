## 核心理念

**不要先問「這個物件要怎麼做」，先問「它需要給玩家什麼感受、在實際鏡頭裡要呈現什麼」。**
美感、玩家注意力、動態、遊戲玩法、技術可行性、Pixel 8 效能與預算是同一個設計問題，不是美術完成後才交給工程「優化」的兩個階段。

一開始不可能預知所有需求；因此不主張無限期規劃。應針對高返工風險做**可逆、便宜、在真正遊戲鏡頭下可驗收的最小樣品**，再決定技術與大規模製作。

### Julia 的任務（每個高價值資產 / 動態製作前）

1. **定義體驗幻想**：玩家應該感受什麼？（例如金髮：高速卻亮麗、俏皮、柔順；不是整頂假髮晃。）
2. **定義主要觀察條件**：實際追車鏡頭 8m、手機解析度、速度、玩家視線焦點。副鏡頭 / 特寫不能取代主鏡頭。
3. **區分三件事**：**幾何／輪廓**（形狀）、**材質／光影**（看起來如何）、**運動／行為**（如何改變）。不要想用物理參數拯救錯的輪廓，也不要用多邊形解決錯的光影。
4. **查詢領域合適技術與工具**：程式生成、Blender、Geometry Nodes、Shader、Instancing、GLB、骨骼、Morph、PBD/布料/粒子等，只比較與此需求有關的 2–3 條，不形成為研究而研究的流程。
5. **判斷製作成本與風險**：可見頻率、遠近、變體數量、互動／碰撞需求、環境相依、授權、手機成本、Codex 使用額度；額外付費預算 NT$0。
6. **給 Codex 一個有停損的小任務**：單一樣品 + 相同條件對照 + 最小可重現測試 + 實測數據 +「什麼情況不繼續」。避免一次做整類、整張地圖或大型框架。
7. **由 Julia 與玩家看實際效果判斷**：驗收「感受」是否達成，而非測試數量、模型面數、工具是否新穎。能用舊方案做得更好時，保留舊方案。

### Codex 的任務

- 開工前閱讀相關的美術規格、鏡頭與性能目標；如果發現**需求目標與選用技術可能不符**，在大量實作前提出最小替代方案，而不是默默選最容易寫程式的方式。
- 測試時分清**美術外形、材質、動態、實際鏡頭可見度**，A/B 盡量只改一個維度；若都不好看，報告是基礎形狀需要修改，不強求物理勝出。
- 大資產、模型權重、暫存工作區留 Repo 外；只把可重用的資產、必要代碼和小型驗收媒體推 dev；本地驗證後才提交。未經玩家授權不動 main，不花額外費用。
- 盡量保留接受過的原型，避免無必要的抽象層、強制轉換全部技術或丟棄工作成果。

### Julia 應主動提醒玩家的時機（討論中自然提醒，不要說教）

- 需求從「主要玩家鏡頭能看見的魅力」滑向「只在特寫顯示的細節」。
- 追求技術完整性、面數／測試通過或新工具，而忘了畫面是否漂亮。
- 為了省效能過早犧牲必需的造型／動態自由度，或為了美觀忽略手機成本。
- 使用者提出會破壞已凍結資產、幾何、動畫或編輯流程的變更；先提醒**返工代價與可逆的替代試驗**，由使用者拍板。
- 屬於新領域（森林、草地、田海、岩壁、群眾、角色、髮絲等），舊的 asset pipeline 未必適用；Julia 先提供技術選擇及成本判斷，避免 Codex 直接套模板。

## 本次金髮案例：該怎麼應用

**感受**：俏麗有型、後側纖細末端受強風拂動；頭頂與大弧線穩定。**主鏡頭**：8m 追車、單側 960×540，大約只有二十多像素的髮型。

- Spring Bones 能改**慣性與延遲**，不能把偏厚的末端自動變纖細。
- Issue #43 A/B（同一 979-tri 幾何）證明 B 機制可行，但未明顯改善實際鏡頭；B 多 ~0.29ms PC CPU/60Hz 畫面，GPU 接近，Pixel 8 未測。
- 優先驗證 **造型／輪廓（細長、漸細、分層）+ 明暗與動態層次**，不是先增大 Spring Bones 的振幅或骨數量；保留 A 當基線。
- 於小螢幕不要追求不可見的「單根頭髮」；利用數束有間隙、具有 1–3 像素輪廓差的髮尾群與金色亮暗，傳達纖細感。此為**待驗證的美術假說**，不是固定像素規格。
- 若新輪廓在靜止 + 高速的主鏡頭成立，才評估局部較長／較鬆的 bone 權重是否比便宜 Morph 更值，否則不再發展完整 Hair Physics Framework。

延伸：森林的主問題可能是遠中近層、輪廓、Instancing/LOD/風動；草地可能是密度、色塊、近距穿幫、過度繪製；船隻是輪廓、水線、航行/浮力。**不同問題，不預設同一技術。**
