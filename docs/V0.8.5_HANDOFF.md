**Status: ready for human playtesting.** Implementation commit: `97cff65`. The local branch is `codex/v0.8.5-scene-streaming`, based on playable v0.8.4 commit `4d2b6ad`. The remote documentation was selectively imported; remote `main` was not merged into the game.

## Start and play

From `C:\astra-dev\OutRun`, with dependencies already installed:

```powershell
npm run dev -- --host 0.0.0.0
```

Vite prints the actual port and LAN address. The server started during this work is listening at `http://127.0.0.1:5174/?stage=1&seed=1` on the PC and `http://192.168.1.105:5174/?stage=1&seed=1` on the LAN. The PC was on Ethernet at this address; a phone must be on the same network. The LAN URL was reached from the PC, but a physical Pixel connection and firewall access remain unverified. For a clean dependency install use `npm ci` before starting the server; on Windows, stop only this project's server first if it holds the native Rollup module open.

Stage 01 uses streaming by default. The development-only `&stream=0` switch retains the old renderer for comparison; production always uses streaming. Play, pause, feedback, photo controls and Stage Codes retain their existing bindings.

## Streaming and route identity

**PASS for the measured Stage:** 1,000-unit road, shoulder, terrain, support, marking, warning and scenery chunks are prepared by a worker. The normal window extends 5,000 units ahead and 1,000 behind; initial startup materialized six chunks (6,000 of 14,450 logical units) instead of all 13 prior road chunks, and at most seven were active in the recorded drives and soak. The initial CPU object inventory (`boot-audit.json`) counted six geometries each for asphalt, shoulders, terrain, support and markings; road detail used 34 and scenery used 20 distinct geometries. These object counts differ from `renderer.info.memory`, which counts uploaded resources. Road work is prioritized ahead of scenery. Main-thread scene commits and disposal are scheduled in approximately 3 ms slices. Shared materials, textures and marker templates survive retirement. The old Stage sampler and physics remain the source of truth.

`evidence/v0.8.5/route-comparison.json` compares the full Stage definitions plus 211 road samples each for seeds 1–3 against the v0.8.4 browser baseline: maximum numerical difference **0**, with no other differences. `v085-road-worker.spec.ts` compares five chunks per seed in forward and reverse order; `v085-scenery.unit.ts` compares reverse-built scenery with the prior full-scene instance placements for all three seeds. Tire-contact, edge, lane-paint, grade and support checks ran against loaded chunks. Rapid window changes and replay were tested for stale work.

## Desktop performance evidence

The final scheduler runs used Edge at 960×540, the same automated driving policy, real-time rendering and the existing Stage Code. Frame statistics exclude frames before the explicit driving-start marker. Measurements are specific to this PC, not promises for another GPU or a physical phone.

| Seed | v0.8.4 baseline ready | v0.8.5 ready | Drive duration | Frame P95 / P99 | Worst driving frame | Frames ≥50 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1,555 ms | 1,216 ms | 119.54 s | 16.8 / 16.8 ms | 33.4 ms | 0 |
| 2 | 943 ms | 1,225 ms | 118.66 s | 16.8 / 16.8 ms | 33.3 ms | 0 |
| 3 | 1,035 ms | 1,188 ms | 119.42 s | 16.8 / 16.8 ms | 49.9 ms | 0 |

Startup is mixed rather than universally faster; seed 3's maximum is close to the 50 ms threshold. Its nearest one-second resource sample was at roughly 57 s and distance 6,591, with all seven visible-window chunks ready and no queued commit work; that sample does not establish the cause of the spike. Every one-second sample in these drives had the current and next two road chunks ready; this sampling alone cannot exclude shorter transients. Each run has a full recording and report under `docs/evidence/v0.8.5/stream-seed-{1,2,3}-budgeted-full.webm` and `stream-seed-{1,2,3}-budgeted-report.json`; `performance-summary.json` includes frame distributions, ready-window samples, resource counts and recent chunk timings. Representative `stream-seed-{1,2,3}-budgeted-mid.png` frames and `stream-scene-999.png` / `stream-scene-1001.png` were visually inspected. These are scripted browser drives, not human playtests.

The per-chunk audit in `chunk-timings.json` captured all 15 chunks: maximum road preparation 42.6 ms, scenery preparation 32.0 ms, individual main-thread commit 0.3 ms, WebGL buffer-upload submission 0.2 ms, and individual disposal step 0.1 ms (726 disposal calls). Preparation is off the render thread; submission time is **CPU-side**. A separate `EXT_disjoint_timer_query_webgl2` audit surrounded 1,762 individual buffer submissions across all 15 chunks (`gpu-upload-query.json`): the largest single query was 0.711 ms and the largest sum attributed to one chunk was 0.858 ms. Driver scheduling can defer transfer work beyond an individual query, so those numbers are not a complete isolated transfer cost. Another final-scheduler 30-second query captured 1,799 whole GPU frames: P95 4.49 ms, P99 5.26 ms, maximum 15.08 ms (`gpu-timing.json`).

With 4× browser CPU throttling, 119 samples over a 30-second keyboard drive showed gas and steering held, about 1,100 units of progress and no unready current/next-two road chunk. A separate test added a one-second delay to each worker response under the same throttle: the initial window took 15.6 s, but all 119 driving samples retained both inputs and had near road ready; replay returned to chunks 0–5 and a new seed loaded correctly (`slow-worker.json`). Delaying delivery simulates preparation latency; it is not a direct measurement of slow worker computation. These are desktop simulations, not Pixel benchmarks.

## Resource and precision checks

**PASS for a repeated existing route:** `soak.json` represents 20 virtual minutes on the budgeted scheduler by repeatedly moving through the existing Stage and allowing each window to materialize. It is a lifetime stress test, not a newly created ten-minute Stage. Active chunks never exceeded seven, geometry counts ranged 84–160, and after warmup the renderer geometry and texture counts were identical whenever the same positions were revisited. JS heap varies with garbage collection.

| Virtual time | Geometry | Textures | Draw calls | Active chunks | JS heap |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 min | 137 | 5 | 238 | 7 | 46.9 MB |
| 5 min | 118 | 5 | 191 | 7 | 46.3 MB |
| 10 min | 160 | 5 | 235 | 7 | 19.8 MB |
| 20 min | 130 | 5 | 284 | 7 | 20.7 MB |

**PASS for the synthetic high-coordinate checks; UNVERIFIED for a real long route:** a test-only straight 81,000-unit RoutePlan drove the actual streamer at progress 70,000; chunks 69–75 became ready, five samples retained four lanes and half-width 7, and surface-height error was zero (`virtual-70k.json` and `virtual-70k.png`). Separately, a synthetic road-and-camera render translated by 70,000 world units changed 39–59 of 518,400 pixels over five poses relative to its untranslated rendering; the maximum sampled Float32 road-width error was 0.0075 units. A synthetic screenshot event preserved absolute photo distance `70000` and Stage-relative event position `69650`, although that event used the existing finite Stage whose sampler clamps beyond its end. These probes do not establish animation or feedback correctness on an actual complex 70,000-unit itinerary. A floating origin was not introduced on this evidence, and no long Stage was added to the game.
