## Target player experience

Launch **Stage 01: Pacific Getaway** (original placeholder name). Select a seed or press `New Route`, then enjoy one uninterrupted ~100–150 second nominal real-play journey at the accepted 1.75× arcade pace. The player sees a coherent scenic adventure through supported coast/canyon/city layers with distinct high-speed sweepers, altitude/crest/downhill, occasional genuinely narrower/wider roads, one clearly readable technical corner and a final scenic release/finish. Free driving is fun and responsive even without money or enemies.

Stage duration comes from authored/generated **DISTANCE**, not a timer that spawns road changes. A player who brakes/stops takes longer; don't have the track disappear or jump after 120 seconds. No need for a multi-stage branch fork now.

### Real procedural generation, not three canned pilots simply concatenated

- Use the v0.7D **true distance-localized placements[] L2** and the 18 existing C/E/W primitive shapes. Reuse the 3 human-KEEP L2 pilot *recipes as strong reference motifs*, but compose a multi-act, fresh Stage using a small seeded `StageRecipe` / `JourneyIntent` with a deliberately simple tension→release→challenge→payoff rhythm.
- Stage must contain multiple local L1 placements per L2 beat, with overlap across C/E/W and orderly transitions on the SAME channel. Do not revert to v0.7C's one whole-route C/E/W triple. A long bend can remain a single complex primitive if that's what makes the experience good; do not artificially split just to hit a count.
- Use seeded variation to change **actual driving content**: order of compatible motifs, turning signs, curvature ramp lengths/efforts, hill crest/valley profiles, lane-width rhythm, and placement of scenic reveals. Mere random palm positions/colors or 16 different seed labels does NOT qualify. Seed variation obeys finite parameter envelopes anchored in previously enjoyable driving, not global AAA path/AI solver. Never silently auto-adjust live grip to force a seed to pass.
- Keep a *coherent Stage One identity* (city-to-coast-to-canyon scenic trip or a similar intentional three-act itinerary). Scene transitions use the existing 3 art packs, not new snow/volcano or expensive high-end city world. Vary micro-details/landmarks while holding a sensible thematic arc. **Stage/L3 biome metadata decides the soft probability and strength of elevation elements,** per `docs/V0.8_BIOME_VERTICALITY_METADATA.md`: canyon strongly favors the most dramatic climbs/crests/descents; city and coast primarily gentle/rolling but CAN have big elevation when visually plausible. Do not ban or rewrite previously KEEP'd dramatic coastal pilots.
- One generator produces successive L2 beats at distance intervals, reconciles C/E/W values/derivatives (position, heading, grade, width) at seams. Terrain & roadside props follow the actual generated 3D road. Render road ahead in predictable reused geometry/visible chunks instead of generating a massive unbounded world at once. Maintain stable camera road ahead and off-road recovery.
- Use exact approved v0.7D.2 driving/feedback baseline: grade force, speed-dependent lateral curve pressure, warmer/quieter appropriately gated skid audio, all keyboard prompts and actual PS4 Gamepad mapping. DO NOT "fix" procedural hard bends by changing these accepted game rules.

## P0 first in this same Goal — minor verified UI/input refinements

The player delegated the decision to merge these refinements with Stage One, so **do not create a separate milestone or demand a second Codex Goal**.

### A. Compact, correctly embedded keyboard accelerators

- On desktop with keyboard as current meaningful input, use a short label with the accelerator embedded in the FIRST appropriate character: `[P]lay` (for Play), `[P]lay again`, `[R]eplay same`, `[N]ext`, `[B]ack`, etc. NO repeated `[P] Play` / `[R] Replay` type prefixes. Use actual existing bindings; never display a fake key.
- Native Tab/Shift-Tab and focused Enter/Space still activate buttons, never also accelerate/brake. Preserve all text/IME suppression and existing accessibility labels. For non-English labels, if there is no matching Latin character, use an unobtrusive short accelerator hint rather than inventing an English translation.
- Gamepad hints show mapped face buttons/d-pad where relevant instead of ALL keyboard accelerators. Mobile touch should not waste screen area showing keyboard keys.

### B. Input-mode-aware presentation (preserve controller and keyboard behavior)

- Source of truth: supported standard gamepad connected AND last meaningful active input vs keyboard/touch. Do not flicker from analog stick polling noise or briefly neutral triggers; switch only when meaningful gameplay/menu interaction indicates a new mode. After gamepad disconnect, switch to available keyboard/touch hints. Mouse input can use keyboard-style hints on desktop if no pad active.
- Do NOT remove existing keyboard shortcut support just because the gamepad is connected; only swap visual hints. Menus and modal should be fully usable with either input source, and switching mid-review must update hints consistently. Gamepad menu dialogs should show visible Cross `✕` confirm and Circle `○` back; keyboard menu shows focused Enter and actual shortcut letter.

### C. In-drive praise/issue hint and PS4 issue action

- Keyboard user sees `[G]讚 · [I]問題` in a safe small area; actual keyboard G/I shortcuts remain. Supported active PS4 controller user sees `L1 讚 · □ 問題` and NOT keyboard shortcuts. Actual `L1` to praise, `R1` remains alternate if prior code implements it; **Square (standard button index 2)** marks an issue without forcing onscreen keyboard text. A short anchored issue flag can be edited after the drive. Show Square mapping clearly in the game and feedback modal.
- While quick praise modal is open, D-pad UP/RIGHT/DOWN/LEFT maps exact `超好玩! / 超刺激! / 超難! 但是過了超爽! / 風景優美`, `✕` commits selected tag and resumes, `○` cancels. Do not let D-pad steer the vehicle in this modal; keep its retrospectively anchored 2–3 second prior actual snapshot and selectable older samples.
- Avoid controller input held/repeated actions and do not lose engine/game-state or silently change the 144px approved touch steering. Test physical-compatible mapping mocked in browser, real hardware state UNVERIFIED unless physically used by user.

## L3 biome / terrain verticality weights

- The Stage generator uses `WorldMeta` for actual playable city/coast/canyon profiles. The most dramatic altitude and climb/descent envelopes should be sampled MORE OFTEN in canyon (later mountain world), not simply shuffled evenly into downtown boulevards and flat seaside roads.
- These are **relative preferences, not exclusions**: ordinary city/coast hills remain, and visually supported exceptional coastal cliff descents or urban ramps are valid. Do not prohibit existing KEEP Pilot A/C profiles or randomly relocate their historic routes.
- Implement the small tunable content map described by `docs/V0.8_BIOME_VERTICALITY_METADATA.md` rather than extensive rule/constraint code. Metadata should steer amplitude/grade profile parameter choices, not only choose an Elevation shape ID; E03 can be a tiny or enormous ridge. Use seeded decisions.
- Scenery and terrain MUST follow grade and world palette: high-verticality canyon roads visually belong in a canyon ridge/valley, while major coastal/city deviations need plausible geometry/landmark treatment. Never visually re-skin a floating cliff as a city street. Smooth grade/elevation continuity through world scene boundaries.
- For a compact deterministic seed batch, test canyon dramatic beats statistically more frequent than city, and keep explicit rare city/coast dramatic examples possible. Do not guarantee every Stage has a canyon mega-crest, and don't preemptively score whether a player will find a road fun.
