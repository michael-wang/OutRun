## Product goal

Prove a scalable creation/review workflow, **without making Michael drive all basic ingredients**:
1. Codex audits/reuses existing geometry and implements a technical catalog of **18 parameterized L1 shapes**: Curvature (8), Elevation (6), Width (4), as defined in `docs/L1_PRIMITIVE_CATALOG.md`.
2. Compose a **systematic first batch of 16 distinct playable L2** from the three independent channels, using the explicit coverage table in `docs/V0.7C_L2_COVERAGE_MATRIX.md` rather than inventing ad-hoc bricks.
3. Let the human drive those L2 and leave immediate **problem OR POSITIVE feedback at the precise moment**, then review each entire L2. Keep it tiny, touch-friendly and local-first.

NO L1 user review or L1 editor in this milestone. No Pacific five-minute trip, mystery generation, general game economy, accounts, traffic or new biomes. This is not permission to rewrite the successful game.

## 1. L1 implementation contract

- **C01–C08, E01–E06, W01–W04** as in catalog. Shape is a parametrizable family, not separate data for every handedness/effort/lane count.
- Compose one resolved geometry profile per road channel at each distance `s`: signed RequiredSteering/curvature, world height/grade, real paved half-width/total lanes. Profile parameters should be readable and testable; limit special-case code.
- Generate actual Three.js centerline/edge/lane lines and consistent offroad classification from the same shared profiles. A 2-lane hairpin and 8-lane mountain ridge must both have believable road/ground relationship.
- L3 world applies supported **Azure Coast / Golden Canyon / Sunlit Coastal City** art, terrain, props and visibility. It chooses road surface/world compatibility; do not treat snow or lava as unrestricted geometry shapes. Road generation precedes terrain/scenery fitting. New render code only where existing v0.7A.1 setup cannot handle new combined height/width.
- Existing accepted gameplay remains: Arcade Lateral Balance, world pace 1.75×, N=4 soft steering detents each side, extreme corners braking where designed, full-speed sweeping, vivid yaw/drift, wheels/occupants/hair, Pixel 8 landscape fullscreen/PWA/two-thumb/hand-swap/anti-long-press, PC A/D+Space/Enter, needle dial left of car, bounded recoverable offroad, fixed camera.
- QA automatically checks pure L1 behavior, sane geometry and reproducibility, but must NEVER mark an L1 as human-fun-approved. No expensive global optimal-path solver, difficulty gate, or speculative reaction-time restrictions.
- Reuse actual v0.7A.1 track generators and scenery APIs first; create adapters before rebuilding.

## 2. L2 batch and presentation

- Use the **16-row matrix** in `docs/V0.7C_L2_COVERAGE_MATRIX.md`. Each item gets a stable ID (L2-001...L2-016), concrete revision+seed+generatorVersion/profile parameters, biome and short intent, 30–60s-ish replayable drive with visual approach/main/exit. Four batches of four for human review.
- Each scene must be materially different in driving shape, width, elevation or world; don't produce 16 labels on the same physical road. A few deliberately simple controls (flat/stable width) are valuable contrasts.
- Reuse v0.7A Brick Lab UI where possible. A new opt-in `?lab=l2` route is recommended; `?lab=bricks`, ordinary free drive and the historical reviews must remain untouched.
- Lab UI: Play / Replay Same / Next / Previous, L2 ID/seed/short objective, 1/4 batch navigation, completion indicator and existing Play/Restart controls. Avoid giant debug HUD; hide advanced profile parameters behind tiny expandable detail.
- Each candidate must have a clearly marked end and an optional Replay; do not let an L2 stretch on indefinitely because its test route loops. Human can evaluate gameplay independently.
- Seeded deterministic road + scenery placement (if randomness used), content fingerprint and profile IDs/parameters. Don't use unfixed `Math.random` to determine reviewable geometry.

## 3. In-drive Feedback — negative and positive, equally important

**User-requested FOUR POSITIVE QUICK TAGS (use exactly these labels in Traditional Chinese):**
1. **「超好玩!」** — key `super_fun`.
2. **「超刺激!」** — key `thrilling`.
3. **「超難! 但是過了超爽!」** — key `hard_but_rewarding`.
4. **「風景優美」** — key `beautiful_scenery`.

Do not bury these inside only the end-of-level review: **the player can mark a positive highlight DURING DRIVING when it occurs**. A negative/issue event is equally first-class, with immediately available short text.

### UX: minimal buttons and safe touch behavior

- Place small **「✨ 讚」** and **「⚑ 問題」** entry controls in a safe unused top corner of the **L2 lab only**, outside forward apex/steering strip/gas/brake and needle HUD; scale for Pixel 8 landscape 960×432 and 844×390 and PC.
- Tap either: **capture exact event anchor immediately** (`s`, L2 ID/revision/seed + C/E/W profile IDs/parameters, current world, time, speed, raw/applied steer, x, road height/grade/width/lane count/offroad as cheap accessible data), then pause/freeze gameplay and release input state safely. For **positive event**, show four large touch-friendly quick tags; one tap selects and saves a positive event (optional short note), and `Resume` returns to driving. For **problem event**, show autofocus short free-text entry (max ~240–400 chars), optional kind (e.g. geometry/visual/controls/other) only if truly useful, Save + Resume or Cancel. Make text input easy with Android landscape keyboard; do not let keyboard key events accelerate/steer.
- Let owner skip typing for positive quick tag. A user may send multiple distinct praise/issue markers at different positions; don't deduplicate intentionally repeated feedback. No automatic sentiment detection; a positive tag is explicit praise.
- Special case **「超難! 但是過了超爽!」**: allow it immediately AFTER completing the difficult moment/L2. End-review may select it and associate the event with **the just-completed L2**, not mistakenly the next challenge/start segment. Preserve pre-completion snapshot (and optionally previous several seconds of inputs only if low-cost). Do not require users to interrupt a challenging maneuver just to praise it.
- Issue and praise markers **remain distinct from global KEEP/REWORK/REJECT votes**; one highlight does not automatically imply KEEP and one reported defect does not automatically REJECT.

### End-of-L2 review

Show **KEEP / REWORK / REJECT** and perceived difficulty **1–5** with understandable labels (1 Easy, 2 Moderate, 3 Hard, 4 Very Hard, 5 Godlike), optional 1-line note and the SAME four positive tags (multi-select or add positive highlights for this completed segment). If a player skipped in-drive markers, end review can still capture what was memorable. Allow incomplete review and return later.
- R1/R2 Brick Lab history remains untouched; each new L2 starts `humanVote=UNREVIEWED` and `difficulty=UNRATED`, whatever its machine QA. No Codex scripted test may leave KEEP or feedback in the user's real browser storage.
- Persist using simple localStorage keyed by `labMode + id + revision + contentFingerprint`. Export **one portable JSON** combining: schema/catalog/generator version, every L2's review/difficulty/notes, positive/issue events with precise anchors, and optional L2 profiles and seed. No account/backend/public upload. Provide an explicit **Export Feedback** control.
- Include a simple human-readable event list in the lab (e.g. “L2-012: 2 praise, 1 issue”), plus **Replay from Reported Location** if cheap and safe; optional P1, not a blocker. Main need is exact reproducible anchor for Codex investigation.
- Explain locally that **export file stays on device until user chooses to share it**. Preserve unshared notes when restarting and avoid hidden network telemetry.

May adjust format to existing local review schema rather than invent migrations; output must remain documented and include both in-the-moment and end review data. No personal identifiers/device secrets, recordings or network calls required.

## 4. QA / evidence — do the work instead of building a methodology

**Engineering L2:** all 16 generated in real playable Three.js browser, sampled screenshots/motion.
