# S1 source audit and measurement definitions

Starting commit: `c22866e2f9f143614b4654a9ffff43e24b624866`, clean `dev`. Issues #7 and #9 read before changes. No route, scenery placement, density, controls, physics, pace, chunk size, streaming window, release or Worker architecture changes.

## Confirmed source behavior

- `StreamedScene.dispatch`: a single outstanding Worker request, non-preemptive. All desired missing roads precede any scenery. Within each class, distance from the current chunk determines priority. A scenery request already running can delay a newly required road. Conversely, repeated new road demand can postpone optional scenery indefinitely if capacity is insufficient. This is a scheduling possibility, not proof of the Pixel 8 incident.
- `receive` queues CPU object creation after transferable data arrives; `working` covers both Worker preparation and unfinished main commits. Road validation requires nonempty asphalt. Scenery is not given an equivalent nonzero-instance requirement: an intentionally empty chunk can legitimately become ready.
- `pump`: nominal 3ms budget, checked between tasks (an individual task can exceed it). Road commits first; pending retirement before scenery. Definition allocation precedes scenery instance attachment, and ready is the final queued task. A partly committed chunk can render some objects while still working. No optional-scenery gameplay hold was added.
- `update`: roots outside the unchanged 1km-behind/5km-ahead window detach immediately; individual disposal is deferred. Queued unwanted work and unwanted Worker results are discarded. Diagnostic retirement timestamps and discard counts distinguish this from generation failure.
- Worker failures restart at most twice; timeout is 30s. Main commit errors are fatal and can leave partial objects attached. Existing safety gate blocks progression on fatal errors, context loss, uninitialized Worker, or insufficient attached road coverage. An exception is not silently interpreted as an empty scene.
- `road-worker.ts`: scenery uses the same deterministic generator; each InstancedMesh's geometry attributes and instance matrices are serialized. Main thread reconstructs geometry and InstancedMesh using those matrices. Generated counts and actually attached counts are separate measurements.
- `scenery.ts`: deterministic act weights select families. Clearance rejection, landmark spacing, canyon bend exclusions, rocky section exclusions and bridge gap (span plus 35m on either side) intentionally suppress some props. Road cut-rock walls live in road geometry, so scenery instance counts alone do not measure all roadside visual content. No density rule was changed.
- `road-chunk.ts`: numeric preparation repeatedly samples absolute route position, width, weights and normals across strips, dashes, edge markings and supports, then merges by material. It shares the Worker with scenery. The timing baseline can identify this phase's cost; it cannot attribute individual internal functions without a CPU profile.
- Culling: Three.js frustum culling remains enabled; InstancedMesh bounds derive from instance matrices. No custom code disables scenery based on readiness. Fog fades from 180m to 1100m; mobile camera far plane is 1400m. An attached mesh may be behind the camera, fogged, terrain-occluded, or only partly in view. No confirmed culling defect follows from `ready` alone.

## Diagnostic definitions and limits

`?streamdiag=1` retains up to 256 scalar road/scenery request records, 900 once-per-second snapshots and 128 stall events. Existing history remains capped at 2000 entries. No per-frame geometry traversal. Per-mesh render callbacks are diagnostic-only; snapshots inspect direct chunk children once per second (or on explicit snapshot/export calls).

Request/response/commit/ready timestamps use the main thread's monotonic `performance.now()` origin. Worker `cpuMs` is elapsed time around synchronous generation/serialization in the Worker, excluding injected delay; it is not an OS CPU accounting counter and can include descheduling. Response latency includes injected delay, Worker preparation, messaging and main-thread delivery. Ready latency is request to final CPU attachment, excluding time before dispatch. Commit CPU is the sum of task durations; commit wall span includes gaps between first and last task. Incomplete requests are excluded from ready latency quantiles and remain in records. Quantiles use nearest rank and include sample counts; they describe the retained requests, not extrapolated lifetime percentiles.

`attachedInstances` counts instances in scenery meshes whose chunk root is currently attached. `recentSubmittedInstances` counts instances belonging to meshes with an `onAfterRender` callback in the last 250ms; this is CPU renderer submission evidence, not per-instance visibility, GPU completion, or visible pixel count. GPU completion, visible pixels and GPU memory bytes are explicitly unavailable (`null`). Existing DEV upload instrumentation measures synchronous `bufferData` submission time only.

Road headroom is contiguous attached ready road from player position divided by speed in world metres per second (handling speed × existing effective pace), not dashboard km/h. At zero speed headroom seconds is null. Near finish the remaining route naturally limits headroom. Readiness checks still use the preexisting safety buffer and remain unchanged.

Renderer geometries/textures/programs are allocation counts; JS heap is a browser-provided proxy when available, never GPU memory. Queue snapshots separate road commits, scenery commits, retirement, pending Worker request and unrequested road/scenery demand. One-second samples can miss transient peaks. Screenshots and full per-chunk records supplement them.

Final retention detail: once-per-second saved samples omit repeated lifecycle records; export `latest.lifecycle.records` contains the full retained set. Direct snapshots also return the records. Record `attachedInstances` is cumulative for that request; `retiredAt` marks detachment, while snapshot chunk counts measure current attachment. `observedWorldTravelSpeedMps` measures distance delta / wall time over the last diagnostic sample interval (null initially or on backward reset); `unheldTravelSpeedMps` and headroom use the existing handling speed × effective pace. `snapshotCpuMs` measures the synchronous diagnostic snapshot itself. The diagnostic label is not a release-version change.
