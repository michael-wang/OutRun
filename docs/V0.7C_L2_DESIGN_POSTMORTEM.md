# v0.7C L2 composition — product NO-GO analysis

**Owner verdict (27 Oct 2026):** 16-L2 batch design was not what the owner meant by a 20–30 second L2. Actual play felt like **one prolonged L1** (one elevation motion or one large bend) per track. The owner rejected the batch as a PRODUCT DESIGN DIRECTION, even though the attached exported review JSON still recorded four specific REJECT votes (L2-001..004) and twelve UNREVIEWED entries. **Do not silently turn the remaining twelve user review records into REJECT**, or imply the user reviewed each one separately.

**Material inspected:** authored remote documentation `docs/V0.7C_SPEC.md`, `docs/V0.7C_L2_COVERAGE_MATRIX.md`, real user L2 review JSON provided in ChatGPT. Actual local source and new 40-second video have NOT been fully inspected in this repo analysis; don't assert exact local generator code behavior or reference-video L1 count.

## Root cause in specification: wrong unit of composition

The whole 16-row coverage matrix defined one **C family + E family + W family + L3 world PER entire L2**. This was a *cross-dimensional overlay*, useful for technical primitive combinations, but not an authored TIME/DISTANCE sequence of many independent local road-driving events.

Example: L2-003 C02 constant arc + E01 flat + W01 constant 8 lanes = effectively **one perceivable geometric event: a long bend**. L2-001 C01 straight + E02 grade + W03 progressive narrowing = often **one primary perceptual event: long climb**. This matches the owner's report.

The specification requested 30–60 seconds and a generic "approach → challenge → exit", but NEVER required multiple placements of L1 of SAME family at DIFFERENT distances or a perceptible sequence of multiple meaningful operations. Codex could satisfy all named data-catalog/coverage/test criteria while making an overlong single action. This is fundamentally a **product-spec acceptance failure**, not evidence that procedural road geometry or the entire L1 implementation is broken.

## Next design cannot be fixed by changing 16 to 20 or hardcoding 3–5 pieces

The owner explicitly said a 3–5 piece count was **an offhand example**, not a specification. They provided a **~40-second gameplay reference video** and requested analysis BEFORE redefining the desired event density/structure.

The analysis should produce a timestamped event table for that exact film and distinguish:
1. **L1 geometric event placements**: curvature transitions (including left↔right within one profile), grade/crest/valley, effective width changes. Record starts/ends and overlaps, magnitude & player action.
2. **Visual/world events**: scene transitions, reveal moments, roadside props, obstacles/traffic, camera/FX shifts (not all of these are implemented L1 geometry).
3. **Vehicle/audio events**: acceleration, braking, audible up/downshift, changes in speed and engine note. These are separate from L1 road primitives.
4. **L2 perceptual structure**: relief/anticipation/demand/reversal/reward, tempo and overlaps. Multiple source-primitive lobe changes may not all be separately perceived; event count is not just the number of lines of source data.

ONLY after actually seeing the film may we decide sensible prototype duration, event-density distribution and how many C/E/W placements to sequence or overlap. The L2 data model must allow multiple PLACEMENTS per channel at different distance anchors, with one resolved effective value per channel; preserve same-distance layering. This is a *design direction*, not an authorized code rewrite without video review.

## The development-process failure

We bundled in ONE costly Goal: 18 basic L1 families + 16 L2 + feedback UI. Automation checked 18-shape/16-row catalog coverage, geometry continuity, screenshots and technically playable drives, but did NOT test whether each long L2 contains a sequence of different player actions. The owner spent time on it and found a scope-level mismatch.

Future correction strategy: first inspect the 40s reference, then implement **ONE playable L2 pilot**, have the owner test its composition, and only after human GO expand to a larger matrix. Human fun must be the product gate; passing unit/E2E cannot fix unclear experience requirements.
